# PLC 데이터 규칙 분석 메모

작성일: 2026-10-12

사용자가 전달한 현장 분석 내용을 정리한 초안이다. PLC 사양서나 실제 수신 원문으로 검증한 확정 프로토콜은 아니다.

## 메시지 형식

```text
[Prefix 1문자][스프레더 위치 숫자 5자리][3000 4자리]
```

총 10문자이다. ASCII 전송이라면 본문은 10바이트이며, CR/LF 등의 구분자가 포함되는지는 확인이 필요하다.

| 구간 | 길이 | 현재 해석 |
|---|---:|---|
| Prefix | 1 | 장비 상태 또는 이벤트 코드 |
| 스프레더 위치 | 5 | 숫자로 표현한 위치. 단위, 소수점, 원점은 미확정 |
| 후행 값 | 4 | 현재 분석상 `3000`. 의미와 항상 고정인지 여부는 미확정 |

설명용 예시: `B012343000` → `B` / `01234` / `3000`.
이 예시는 실제 PLC에서 수집한 데이터가 아니다. 위치 값의 앞자리 0은 원문에 보존한다.

## Prefix 해석

| Prefix | 전달받은 의미 |
|---|---|
| A | Laden 상태에서 Hoisting |
| B | Idle 상태에서 Hoisting |
| E | Twist Lock |
| F | Twist Unlock |

Laden은 컨테이너를 든 상태, Idle은 컨테이너가 없는 상태로 이해한 초안이다.
Hoisting이 상승만 의미하는지, 하강을 포함한 호이스트 동작을 의미하는지는 확인이 필요하다.
E/F가 명령, 동작 중 상태, 완료 신호 중 무엇인지도 아직 확정하지 않는다.

## 관찰된 작업 순서

### 컨테이너 픽업

작업: Idle 상태 → Hoist Down → 컨테이너 픽업 → Hoist Up

```text
B → F → E → A
```

현재 해석: 컨테이너 없음 → Unlock → Lock → 컨테이너를 든 상태.
각 코드의 정확한 발생 시점과 하강/상승 구간의 대응은 실제 로그로 확인해야 한다.

### 컨테이너 하차

작업: Laden 상태 → Hoist Down → 컨테이너 하차 → Idle 상태로 Hoist Up

```text
A → E → F → B
```

현재 해석: 컨테이너를 든 상태 → Lock → Unlock → 컨테이너 없음.

위 순서는 현재 전달받은 패턴이며, 모든 작업에 강제되는 상태 전이 규칙으로 사용하지 않는다.
연결 중간 진입, 같은 코드 반복, 메시지 누락 가능성도 실제 기록으로 확인한다.

## 구현 전에 확인할 내용

- 앱이 이 데이터를 수신하는지, PLC로 송신하는지, 양방향인지.
- 실제 메시지 원문과 HEX 바이트, CR/LF 또는 시작/종료 구분자의 유무.
- 10문자 고정 길이인지, `3000`이 항상 동일한지와 그 의미.
- 위치 값의 단위, 배율, 범위, 원점, 음수 표현 여부.
- A/B가 상승·하강 모두에서 나오는지, 정지 중에도 유지되는지.
- E/F가 상태인지 일회성 이벤트인지, 잠금 완료를 의미하는지.
- 전송 주기, 반복 메시지, baud rate, data bits, stop bits, parity, flow control.

## 앱 구현 시 검증 기준

USB 수신 콜백 한 번이 메시지 한 건이라는 보장은 없다. 수신 버퍼에서 메시지를 조립해야 한다.
구분 방식 확정 후 다음 사례를 검증한다.

- 정상 메시지 한 건, 여러 건이 붙어 들어오는 경우, 한 건이 나뉘어 들어오는 경우.
- 앞자리 0이 포함된 위치, 잘못된 Prefix, 숫자가 아닌 위치 값.
- 연결이 메시지 중간에서 시작하거나 끊긴 경우의 재동기화.
- 실제 픽업/하차 기록과 코드 순서 및 위치 표시가 일치하는지.

## 2026-10-26 실측 자료에 따른 정정

10월 26일 CSV의 7,343개 메시지는 LF + ASCII `15` + U+FFFD로 남은 미상 구간 + 제어값 1바이트 + 숫자 9자리 + CR로 조립됐다. 기존 문서의 ASCII 알파벳·후행값 3000 고정은 실측과 일치하지 않는다. 제어값은 02(^B) 5,556건, 01(^A) 1,712건, 06(^F) 38건, 05(^E) 36건, 04(^D) 1건이다. ^A 등의 글자는 제어값의 화면 표기이며 ASCII A를 수신했다는 뜻은 아니다.

뒤 숫자 9자리는 앞 5자리와 뒤 4자리로 구분하여 표시할 수 있지만 물리적 단위·후행값 의미는 미확정이다. 후행값 2000/4000/4027 등이 관측됐다. 15의 의미와 미상 바이트의 값도 확정하지 않는다. 영상에는 10월 8일, CSV에는 10월 26일로 표시되어 동일 작업 시점의 값이라고 가정하지 않았다.

1.6부터 원본 바이트는 CSV raw_hex로 보존한다. 기존 �의 원래 바이트는 소실되어 복원하지 않는다. 04(^D)는 별도의 미확정 상태로 취급하며 기존 A/B/E/F 작업 패턴을 연결하지 않는다. 이 실측은 제어값과 필드 형식을 뒷받침하지만 앞서 전달받은 물리적 상태 정의 전체를 확정하는 자료는 아니다.

## 1.7 상태 이력의 기록 기준

파일은 UTF-8이며 원시 제어값을 HEX와 caret 표기로 적는다. 실제 제어 바이트가 바뀔 때 세션 내 순번을 증가시키고 숫자만 바뀌면 원문 CSV에만 계속 남긴다. 구형 ASCII B(42)와 제어값 02(^B)의 차이도 기록한다. 미확정 C0 값은 숫자 9자리와 CR 종료로 구조가 완성된 경우에만 기록하며 물리적 의미를 부여하지 않는다. 알려지지 않은 값으로 기존 작업 순서를 이어 판단하지 않는다.

position_raw/tail_raw는 9자리 숫자의 5자리/4자리 임시 분리 명칭이며 제조사에서 확정한 필드명·단위가 아니다. 전체 숫자와 원본 바이트는 CSV raw_hex에 남기므로 추후 규격에 맞춰 다시 해석할 수 있다.
